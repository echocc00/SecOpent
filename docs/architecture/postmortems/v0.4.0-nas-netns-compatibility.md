# Postmortem: v0.4.0 NAS 升级失败 — netns sidecar 与"受限 Linux"

> **日期**: 2026-08-07（事故 2026-08-06 14:00-15:10）
> **影响**: 绿联 NAS DXP4800PLUS 上 v0.2.0.2 → v0.4.0 升级失败，端到端评估不可用，回滚 v0.2.0.2
> **严重度**: High（核心功能完全不可用，数据无损）
> **事故报告**: operator 程泽杰现场报告；本文为代码侧核实 + 根因整理
> **状态**: 根因已定位；**修复 F1-F4 已实施为 v0.5.1**（F5 由 F1/F2 达成，F6 文档随 v0.5.1 落地）

## 1. 问题清单（逐条代码核实）

### P1｜alembic baseline 与既有 schema 冲突（设计缺口，非 bug）

**现象**: `alembic upgrade head` 报 `table core_appmodels already exists`。

**核实的原因**（`infrastructure/db/session.py:37-72`）:
- v0.2.0.2 时代的 DB 由 `SECOPTENT_DB_INIT=always` + `create_all()` 建表，**没有 `alembic_version` 行**。
- v0.3.0 引入 alembic 后，`init_db()` 对"已有表"的 DB 不做任何事（`auto` 模式跳过 create_all，**也不 stamp**）；`_stamp_head()` 只在"新建表"路径且 `SECOPTENT_DB_STAMP_ON_INIT=1` 时执行。
- 于是 alembic 视该 DB 为"未迁移"，从头跑 baseline migration → 撞已存在的表。

**根因**: W4-D 设计了 `secopent db upgrade/stamp` CLI 供 operator 手动处理，但 **"v0.2.x 存量 DB 升级前必须先 stamp baseline" 这条路径既没自动化也没写进 release notes**。operator 手动 `INSERT INTO alembic_version` 后才通过。

### P2｜netns sidecar 强制路径 + 无能力探测 + 无降级（致命，三层叠加）

**现象**: `POST /start` 返回 200，但后台任务立即崩溃：
```
Cannot create namespace file "/run/netns/secopent-asm-XXX": File exists
CalledProcessError: ['ip', 'netns', 'attach', 'secopent-asm-XXX', '2257604'] returned non-zero exit status 1
```
评估永远停在 QUEUED，nuclei 容器不启动，无 FAILED 状态、无失败审计。

**核实的原因链**（三个缺陷叠加）:

1. **平台假设 ≠ 能力探测**（`infrastructure/egress/netns_isolator.py:126-128`）:
   ```python
   def is_supported(self) -> bool:
       return sys.platform == "linux"
   ```
   只看平台不看能力。绿联 NAS 是 Linux（kernel 6.12.30+）→ 恒 True，但其 iproute2/dockerd 组合不支持 `ip netns attach`。
2. **加固功能不降级**（`interfaces/api/routers/assessments.py:289-296`）:
   ```python
   if (netns_isolator is not None and netns_isolator.is_supported() and make_nft_enforcer is not None):
       netns_handle = netns_isolator.create(assessment_id)  # ← 无 try/except，直接抛
   ```
   netns 是**防御加固**（egress 隔离），不是核心功能；但它失败时直接杀死整个评估。`elif make_nft_enforcer(None)` 的默认 netns 降级分支**存在却不可达**（is_supported() 恒 True 时永远走第一分支）。后台任务异常被 BackgroundTasks 吞掉（仅日志）→ HTTP 200 + 评估永久卡 QUEUED。
3. **部分失败留残留**（`netns_isolator.py:79-113` + router `finally` 326-333）:
   `create()` 三步非原子：`ip netns add` → `docker run sidecar` → `ip netns attach`。attach 失败时 `create()` 抛异常，**`netns_handle` 未赋值 → finally 的 `destroy()` 被跳过** → sidecar 容器 + netns 文件残留。下次评估 `ip netns add` 撞残留 → `File exists` → 死循环。
   附带 bug：`create()` docstring 声称 "idempotent on Linux"——**不实**，`ip netns add` 对已存在名称报错。

**"Device or resource busy" 的机制**: 残留的 sidecar 容器仍持有 netns 引用（`docker rm -f` 从未执行），所以 `rm /run/netns/secopent-*` 报设备忙。**正确清理顺序**: 先 `docker rm -f $(docker ps -aq --filter name=secopent-netns-)`，再删 `/run/netns/secopent-*`。

### P3｜11 个测试 fail（测试环境依赖，暴露同类问题）

**核实**:
- `tests/infrastructure/test_netns_sidecar.py` 的 real-docker 测试只在 `sys.platform != "linux"` 时 skip（`:189`）——在 NAS（Linux）上**真跑** `ip netns`，必然 fail。CI 的 ubuntu-latest 有完整 iproute2 → 绿。
- 4 个 interface 测试（outbox_wiring / start_oracle ×2 / race）经 TestClient 同步走到 `_run_assessment_daemon` 的真实 netns 分支——同样环境依赖。**接口层单测不应触碰真实内核能力**，这是测试设计缺陷。

**根因**: 测试的"平台门控"与生产的"平台假设"是同一个错误——用 platform 代替 capability。

### P4｜文档缺口

- v0.4.0 release notes 提 "Netns sidecar 绑定 (Phase 2.3, Linux)"，但没写: 需要标准 iproute2（含 `netns attach`）、NAS 类受限 Linux 不兼容、`SECOPTENT_*` 关闭开关（当时也不存在）。
- 无兼容性矩阵文档；operator 只能靠升级试错发现。

## 3. 根因分析

### 因果链（一次评估的完整崩溃过程）

```
POST /start → 200（BackgroundTasks 在响应后执行）
  └─ _run_assessment_daemon
       └─ is_supported() == True（NAS 是 Linux）
            └─ create(): ip netns add ✓ → docker run sidecar ✓ → ip netns attach ✗（NAS 不支持）
                 └─ CalledProcessError 上抛（无 catch）
                      ├─ netns_handle 未赋值 → finally 跳过 destroy → 残留 sidecar + netns 文件
                      ├─ BackgroundTasks 吞异常（仅日志）→ 评估永久 QUEUED，无 FAILED、无审计
                      └─ 下次评估: ip netns add → File exists → 同样崩溃（死循环）
```

### 设计根因

1. **平台假设 ≠ 能力探测**: 对内核/工具链能力的判断必须来自**实际探测**（probe），不是 `sys.platform`。同类: P3 的测试门控。
2. **加固功能反客为主**: 防御性增强（netns 隔离）失败时不得阻断核心功能（扫描）。对照: 同文件的 nft `apply_scope` 就是 best-effort + 审计降级的正确姿势（`execution.py:346-356`）——netns create 没有对齐这个既有模式。
3. **非原子多步操作无自清理**: add→sidecar→attach 任一步失败必须回滚已完成的步骤（create 内部自清理），而不是依赖调用方的 finally（调用方拿不到 handle 就无法清理）。
4. **存量 DB 升级路径靠人肉**: alembic 引入时未把"已有 create_all 表 → 自动 stamp baseline"做成默认行为。

### 过程根因

- CI 只有 ubuntu-latest（标准 iproute2），NAS 类受限 Linux 不在任何测试矩阵。
- realism tier 证明了"DB 并发模型在目标环境成立"（5/5 pass），但**没有覆盖内核能力维度**——realism ≠ 全环境兼容。
- release notes 无兼容性声明规范。

### Bug 类别提炼（归入经验库）

**"平台能力假设"类**: 用 `sys.platform`/OS 版本推断具体工具链能力（iproute2 netns、nft、docker 特性）→ 在定制内核（绿联/群晖/QNAP NAS）上恒 True 但实际不可用。
**处方**: ① 能力探测用真实 probe（add/del 一次性试探 + 缓存结果）；② env 开关兜底（`SECOPTENT_NETNS_ENABLED`）；③ 加固功能失败必须降级到无加固路径 + 审计告警，绝不阻断核心功能；④ 多步系统级操作必须自清理部分失败。

## 5. 修复方案（upstream，目标 v0.5.1）

| # | 修复 | 内容 | 状态 |
|---|---|---|---|
| F1 | **能力探测 + env 开关** | `is_supported()`: Linux 且 `SECOPTENT_NETNS_ENABLED != "0"` 且一次性 probe（`ip netns add/del __secopent_probe__`，结果缓存，失败 → False + warning） | ✅ `c952ed6` |
| F2 | **daemon 降级** | `_run_assessment_daemon` 包 try/except: netns create 失败 → 审计 `netns.unavailable.degraded` + 回落 `make_nft_enforcer(None)`（默认 netns），评估继续 | ✅ `494243d` |
| F3 | **create 自清理 + 诚实文档** | attach/run 失败时 create 内部先 `docker rm -f sidecar` + `ip netns del` 再抛；删除 docstring 虚假的 "idempotent" 声明 | ✅ `c952ed6` |
| F4 | **存量 DB 自动 stamp** | `init_db` 无版本号 → stamp baseline；`secopent db upgrade` CLI 同样自动 stamp（停服迁移路径）| ✅ `d22b218` + CLI |
| F5 | **测试去环境依赖** | 由 F1/F2 达成（受限 Linux 探测 False → 降级分支；real-docker 测试走能力门控）| ✅ 随 F1/F2 |

**否决项**: 长期本地 patch（现场 Fix A）——每次升级需重打，且上游永不知道真实故障面。本方案即其 upstream 化。

**验证计划**: F1/F3 单测（注入 runner 模拟 add 失败 / attach 失败 / 全失败，断言探测缓存、自清理、降级路径）；F2 接口测试（fake runner 抛异常 → 评估仍 COMPLETED + 降级审计存在）；F4 单测（create_all 后无版本号 DB → init_db 自动 stamp → upgrade head 绿）；NAS 现场复测由 operator 在 v0.5.1 执行。
