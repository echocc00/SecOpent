# v0.5.2 Egress-Execution-Integrity Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make a "container failed but assessment completed with zero findings" impossible, by (1) surfacing container exec failures as step failures, (2) making `coverage_rate=0` with zero successful steps mark the assessment FAILED, (3) dumping `docker logs` on container launch failure, and (4) promoting nft egress-guard absence from a silent warning to an audited hardening downgrade.

**Architecture:** All changes are in the execution path only. Step 1 adds an `exit_code != 0 → StepFailure(WORKER_UNAVAILABLE)` branch in `AdapterStepRunner` (the missing piece from the W3 AdapterRunner→RealScanRunner migration). Step 2 adds a zero-success invariant in `execute_assessment` that `fail()`s before `complete()` when every step of the plan errored/denied and produced zero observations. Step 3 makes the executor's failure surface carry a `docker logs` dump into the observation path. Step 4 upgrades the nft best-effort downgrade to emit a `egress.hardening_unavailable` audit event (aligned with the v0.5.1 netns.degraded pattern).

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy, pytest (coverage gate 80%), mypy strict, ruff, `scripts/lint_forbidden_patterns.py`.

---

## Context: root cause (from v8 issue analysis)

Two independent failure surfaces on the NAS produced one indistinguishable symptom (`coverage_rate=0.0, findings=0, status=completed`):

1. **nft `apply_scope` failed** → [execution.py:387](src/secopent/application/execution.py:387) logged `warning` + continued on app-layer guard. The app-layer EgressGuard only throttles in-process egress — it **cannot** block a nuclei container on `bridge` network. Network-layer egress isolation was silently lost.
2. **nuclei container launch failed** → `subprocess.run` raised; the error surfaced as a bare `Error: No such file or directory` with no `docker logs` dump. Worse, **`RealScanRunner.scan` never checks `exit_code`** ([real_scan.py:162](src/secopent/infrastructure/adapters/real_scan.py:162) returns `RealScanResult`; [step_runner.py:128](src/secopent/infrastructure/adapters/step_runner.py:128) ignores it). So all 9 steps "succeeded" with 0 observations → `complete()`.

The pre-W3 `AdapterRunner` ([base.py:244](src/secopent/infrastructure/adapters/base.py:244)) *did* classify `exit_code != 0` as `OutputStatus.PARTIAL` with errors — that semantic was **dropped** in the migration to `RealScanRunner`. This plan restores it.

**Deliberately out of scope:** NAS environment fixes (`apt install nftables`, docker socket group, residential egress) and "run nuclei on the ECS" guidance — those are operator actions covered by the v8 issue §4/§6, not code.

```python
def _scan_target(self, step: PlanStep, target: str) -> RealScanResult:
    args, mounts = self._invocation(step.runner, target)
    try:
        result = self._scanner.scan(step.runner, args=args, mounts=mounts)
    except ContainerExecError as exc:
        raise StepFailure(FailureClass.WORKER_UNAVAILABLE, str(exc)) from exc

            f"adapter {step.runner!r} exited {result.exit_code} on {target}: "
            f"{result.stderr.strip() or 'no stderr'}",
        )
    return result
```

```python
class ContainerExecError(DomainError):
    """The tool container could not be launched (docker run failure)."""


def _docker_logs(container: str, docker_bin: str = "docker") -> str:
    """Best-effort `docker logs --tail 40` dump for diagnostics (v0.5.2)."""
    import subprocess
    try:
        proc = subprocess.run(
            [docker_bin, "logs", "--tail", "40", container],
            capture_output=True, encoding="utf-8", errors="replace",
            timeout=10, check=False,
        )
        tail = (proc.stdout or proc.stderr).strip()
        return tail[-2000:]
    except Exception:  # noqa: BLE001 - log dump must never mask the exec error
        return "<docker logs unavailable>"
```

In `RealScanRunner.scan`, wrap the executor call:

```python
try:
    result = self._executor.run(
        image_digest=self.image_ref(adapter_key),
        command=list(args),
        mounts=dict(mounts or {}),
        network_policy="bridge",
        resource_limits=dict(
            resource_limits or _ADAPTER_RESOURCE_LIMITS.get(
                adapter_key, _DEFAULT_RESOURCE_LIMITS
            )
        ),
        capabilities=list(capabilities or _ADAPTER_CAPABILITIES.get(adapter_key, ())),
    )
except Exception as exc:  # noqa: BLE001 - container launch failure
    hint = f" (see `docker logs {adapter_key}` for the container)"
    raise ContainerExecError(
        f"container launch failed for {adapter_key}: {exc}{hint}"
    ) from exc
```

Then the empty-execution gate, before `service.complete`:

```python
# v0.5.2: an execution where EVERY step failed and nothing was produced is
# an empty execution, not a clean scan. Mark FAILED so `coverage_rate=0.0`
# never masquerades as "target is clean" (v8 NAS incident).
if not findings and succeeded_steps == 0:
    service.fail(assessment_id, "EMPTY_EXECUTION:no plan step succeeded, 0 findings")
    _audit_record(
        audit_repo, audit_chain, actor="system",
        action="assessment.completed.empty_execution",
        resource_type="assessment", resource_id=assessment_id,
        payload={"coverage_rate": 0.0, "reason": "zero successful plan steps, zero findings"},
        outbox=audit_outbox,
    )
    _logger.warning("assessment empty execution", assessment_id=assessment_id)
    return
```

> Why `succeeded_steps == 0` and NOT `not observations`: a legitimate scan of a clean target yields `findings == 0` but its steps still `SUCCEEDED` (e.g. nuclei ran and matched nothing). Using the jobs signal distinguishes "scanned, found nothing" (COMPLETED) from "never ran" (FAILED). This is exactly the v8 failure: 9 steps all errored → 0 succeeded → FAILED. A plan where ≥1 step succeeded with 0 findings stays COMPLETED (partial coverage is valid, and `coverage_rate` already reports the partial value).
>

## Addendum (v8 deep-dive, 2026-08-07): T7 + T1 correction

After the first implementation, operator analysis of the NAS logs corrected two
attributions and exposed a third failure mode T1-T4 don't cover:

**T1 correction** — the initial fix treated ANY `exit_code != 0` as
`StepFailure`. That is wrong for checkov: it exits `1` when it FINDS policy
violations — a legitimate successful scan (the findings are in stdout,
`tests/e2e_real/test_orchestration.py:371` asserts observations non-empty).
Revised: only `exit_code != 0 AND not observations` fails (indistinguishable
from a broken scan). A non-zero exit WITH observations is a valid result.

**New failure mode (v8 scenario #3)** — "container ran, exited 0, but produced
zero observations" (every probe/template failed, e.g. an ISP throttling 13.5k
HTTPS probes). T1 (exit_code) misses it (exit 0), T2 misses it (no launch
failure), T3 misses it (steps SUCCEEDED). This is genuinely ambiguous with a
clean target — nuclei exits 0 either way — so the assessment stays COMPLETED,
but the `assessment.completed` audit payload now carries
`no_observations: True` so the anomaly is queryable instead of being
indistinguishable from "clean". (`FindingCorrelation` always yields ≥1 finding
per non-empty observation group, so `not findings ⟺ not observations`; the
flag keyed on observations is the honest signal.)
