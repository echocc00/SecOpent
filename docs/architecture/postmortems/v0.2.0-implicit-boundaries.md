# v0.2.0 隐式边界与同步热路径副作用 Postmortem

> **状态**: v0.2.0 (commit `3bfa524`) 发布后 2026-08-05 部署回滚时的根因分析。
> **设计来源**: 用户真机部署 (DXP4800PLUS NAS) 报告的 3 个 issue (`SecOpent-issues-package.zip`) + 代码对照分析。
> **受众**: 所有 SecOpent 开发者;进入下一个 release 前必读。

---

## TL;DR

v0.2.0 release 在生产环境暴露 **2 个 High 严重性的真 bug** (v3 race + v4 lock),与已修的 v2 一起揭示了一个**类别**问题:**"隐式的事务/连接边界 + 同步热路径副作用"**。本项目的整个 W2/W3/W4 修缮(架构清理)也源于同一类**元问题**——**"已建未接线"**(组件测试通过但端到端不工作)。

v3 + v4 的**根因类别相同**(隐式跨边界),**处方不同**:v3 修在代码层 (`session.commit()` 1 行),v4 修在设计层 (**Transactional Outbox** + `busy_timeout` 缓解)。"已建未接线"修在流程层 (**integration graph + production-realism tests + walking skeleton**)。

## 1. 3 个 issue 的客观分析

### Issue v2 — end-to-end 0 findings ✅ 已修 (v0.1.6)

CHANGELOG `[0.1.6]` 4 个 fix (A1-A6) 完整覆盖 (template_host_dir / scan_timeout / nuclei 2g / mkstemp db)。**无遗留**。

### Issue v3 — start_assessment race condition ✅ **真实**

**根因 (3 层,全部已验证)**:

1. **`service.start()` 写 QUEUED 但无 commit** — `application/assessments.py:158` `self._repo.add(updated)` 后 return,无 flush/commit。SQL 已 prepared 但未执行。
2. **路由在 commit 前就 spawn daemon** — `interfaces/api/routers/assessments.py:251-330` 调用 `service.start()` 后立即 `threading.Thread(target=_run).start()`。FastAPI session Depends 在 generator exit (路由 return 后) 才 commit。
3. **daemon 通过独立连接读 db** — `_run` 调 `db.open_session()` 拿独立 connection。SQLite WAL 下,**跨连接的 uncommitted write 不可见** → daemon `get(asm_id)` 看到 stale `APPROVED` → `mark_running` 严格状态机抛 `"cannot run from approved"` → 状态机不一致 (db.queued + audit.failed)。

**修复建议正确性**:
- `session.commit()` (1 行, **彻底修复**) ✅ — 验证过 `flush()` 不够 (flush 发 SQL 但不 commit;WAL 隐藏 uncommitted)。
- BackgroundTasks (**根因级**) ✅ — FastAPI 保证 response flush+commit 后才跑 background task,消除整个 race 类。
- Approach B (mark_running 容忍 APPROVED) / C (fail 接受 QUEUED) — **不推荐**(状态机变得不严格,掩盖同类 race)。

**根因 = 设计 + 代码,设计为主**:
- **设计**: 架构 = "请求线程写状态 → spawn 后台 daemon → daemon 独立连接读状态"。这跨了事务、跨了连接、跨了线程,但没有任何层显式声明。WAL 跨连接可见性是设计时未考虑的语义。
- **代码**: `service.start()` 无 commit;路由无显式 commit。两者必须**同时**存在才会 race。

**v0.2.0 状态**: **未修**。W2-A/W3/W4/W4-B 的改动均未触及此 race(它们都围绕"应该接什么",而非"这个 race 是否修了")。

### Issue v4 — v0.2.0 SQLite lock ✅ **真实**

**根因 (2 层,全部已验证)**:

1. **每个 audit event 双写** — `application/execution.py:113-133` `_audit_record` 注释明确 *"Record to the DB-backed AuditService **and**, if wired, the signed AuditChain"*。实现 line 125-133:
   ```python
   audit.record(...)           # AuditService → core_audit_events      (INSERT 1)
   if audit_chain is not None:
       audit_chain.record(...) # AuditChain → self._store.append()    (INSERT 2)
   ```
   `self._store.append` (`infrastructure/repositories/sqlalchemy_audit_chain.py:62-65`) **每事件** `with self._database.open_session() as session` 开新 connection + commit。**每个 audit event = 2 个 INSERT + 2 个独立 connection commit**。
2. **`busy_timeout=5000` ms** — `infrastructure/db/sqlite.py:104`。SQLite WAL 单写者;高频 (mark_running + 9 plan steps + 错误 audit) → 锁持有时间累积超过 5s → `database is locked`。

**修复建议正确性**:
- `busy_timeout=60000` (Approach B, **缓解**) ✅ — 消除症状,不解决"签名审计在热路径"的根因。issue 自己承认 *"honestly, Approach B is sufficient for v0.2.x"*。
- retry on OperationalError (Approach C, **代码级加固**) ✅ — 无论 busy_timeout 多大都健壮。
- 切 PostgreSQL (Approach D, **生产根因**) ✅ — release notes 已声明 PG 是生产目标。

**根因 = 设计为主 (W3-C 引入)**:
- **设计**: W3-C 把**签名审计作为热路径的同步第二次写入**。v0.1.5 = 1 INSERT/event (够 5s timeout)。v0.2.0 = 2 INSERTs/event + 独立 connection per event → 锁持有时间约翻倍 + 跨 connection 串行化加剧。
- **代码**: `busy_timeout=5000` 对双写负载过低;`SqlAlchemySignedAuditEventStore.append` 每事件 `open_session()` (可改为接受外部 session,合并到同事务 = 1 个 WAL frame)。
- **测试设计缺陷** (issue 正确指出): 单元测试用 `sqlite:///:memory:` → SQLAlchemy 默认 `StaticPool` (单连接,无争用)。**完全掩盖**了生产的 `NullPool` 行为。1190 unit tests pass ≠ production 行为验证。

**v0.2.0 状态**: 引入。W3-C (commit `6574fcf` + 后续) 引入 `core_signed_audit_events` 表 + 双写。

## 2. 整个 W2/W3/W4 修缮的"已建未接线"元模式

W2-A → W4-E 的整个修缮(2-3 周密集工作)是在**补"组件存在但未端到端接线"**。这不是写代码的错,是**开发方法的错**:

| 驱动方式 | 症状 |
|---|---|
| **组件驱动** (本项目 W2/W3/W4 之前) | 每个组件单独看都正确、都测试通过,但**端到端不工作**——因为没人验证"组件 A 的输出是否真的喂给了组件 B 的输入"。 |
| **集成驱动 / Walking Skeleton** | 先跑通最薄的全链路端到端流程(哪怕只做 1% 的功能),然后在此之上增量加功能。 |

**本项目 W2/W3/W4 之前的盲点**:
- ✅ 单元测试覆盖:每个 application service 单独测
- ✅ 集成测试覆盖:每个 adapter 单独测 (`tests/e2e_real/test_orchestration.py` 等)
- ❌ **production-realism 测试**:`start_assessment` 完整链路 (HTTP → service.start → daemon.execute_assessment → 9 plan steps → audit) 用真机 + 真 DB 跑过吗? **从来没有**。直到 v0.1.5 NAS 部署才暴露 v2 + v3。

**W2/W3/W4 的所有 wiring 工作** (W2-A 授权链接线 / W3-A oracle 接线 / W3-C 审计持久化 / W4-A peer-agent 接线 / W4-C OOB canary 接线) 都是因为**没人验证端到端** → 上线时**全部未工作**, 只能修修补补。**如果开发期就有 production-realism tier 的端到端测试,这些 wiring bug 大部分会在 CI 暴露,不需要 v0.1.5 部署才发现**。

## 3. 从这些 bug 提炼的设计原则 (可迁移)

### 3.1 Make illegal states unrepresentable (Yaron Minsky)

**v3 处方**: `mark_running(QUEUED→RUNNING)` 现在用 exception 守门。**非法状态本身可被构造**——`Assessment(status=APPROVED)` 然后 `mark_running()` 才报错。治本是用类型系统:

```python
# 坏: 所有状态一个类,靠 runtime check
@dataclass class Assessment:
    status: AssessmentStatus  # 任何值
def mark_running(self):
    if self.status != QUEUED: raise  # 事后拦截

# 好: 每个状态一个类,根本不能 mark_running 一个 QUEUED 状态
class AssessmentQueued: ...  # 只有 mark_running 可调用
class AssessmentRunning: ... # 只有 complete/fail 可调用
def mark_running(a: AssessmentQueued) -> AssessmentRunning: ...
```

或用 `XState` / statecharts 把状态机变成**数据**而非 exception。**好处**: v3 这种 race 直接被类型系统消除 ("cannot run from approved" 变成**编译/类型错误**而非 runtime 错误)。

### 3.2 Parse, don't validate (Alexis King)

**v3 处方**: `repo.add(updated)` + "希望它在某个时刻被 commit" 是**验证**而非**解析**。边界应该是: 要么"我有一个完整的事务", 要么"我没有"。

具体到本项目: 审计/业务写入应该用**显式的 Unit of Work**:

```python
with db.begin() as uow:       # 显式事务边界
    uow.assessment_repo.add(updated)
    uow.audit_chain.record(...) # 同事务,同 connection,同一 WAL frame
# commit 在这里原子发生
```

**v3 + v4 同时消失**: v3 因为事务在 spawn daemon 前就 commit 了;v4 因为双写在**同一 connection 同一事务**里, 2 个 INSERT 变成 1 个 WAL frame, 锁持有时间回到 v0.1.5 水平。

### 3.3 The Outbox Pattern (Chris Richardson)

**v4 的根本处方**(也是 v0.2.0 release notes 暗示的 PG 方向的精神):

```
业务事务: 写业务表 + 写 outbox 表 (同事务)  → 原子、跨 connection 可见
后台 worker: 读 outbox → 写 core_audit_events → 写 core_signed_audit_events
                                        → 失败可重试、不阻塞主链路
```

**好处**:
- 业务写入和审计**原子** (无 v3 类 race, 无 v4 类锁竞争)
- 签名审计从热路径剥离 (不阻塞 orchestrator)
- 跨进程/重启的可靠投递 (outbox 表就是真相之源)
- **一次解决 v3 + v4**, 且对未来加更多审计消费者 (metrics/告警/转发) 零侵入

### 3.4 The Pit of Success (Mark Miller)

**v3 + v4 处方**: 让"错的写法"**难写**,让"对的写法"**自然**。
- v3: 如果 `service.start()` 内部**自动** commit (事务边界在领域层,而非调用方), 调用方不需要懂 FastAPI session 生命周期
- v4: 如果 `SqlAlchemySignedAuditEventStore.append` 默认**接受**外部 session (合并到调用方事务), 默认配置就是正确的;如果不传 session 则**明确 warning** ("per-event connection, may contend under load")

### 3.5 Explicit over Implicit

v3 的核心: 事务边界、连接边界、线程边界**全部隐式**。**规范**: 每个跨边界点都有一行**显式注释**或**显式参数**说明这个边界。

```python
# 坏
def execute_assessment(audit: AuditService, ...):  # 隐式: audit 可能是 AuditChain
    audit = AuditService(audit_repo)  # 隐式: shadowing 参数
    audit.record(...)  # 不知道写到哪

# 好
def execute_assessment(*, audit_recorder: AuditRecorder, ...):  # 协议类型, 不撒谎
    audit_recorder.record(...)  # 明确: 写到实现决定的存储
```

### 3.6 Local reasoning / Minimize blast radius

v3 的 daemon 通过**参数 + 闭包 + app.state** 拿所有依赖 (`assessments.py:_run` 是个大型嵌套闭包)。**任何一处改动都要推理整个调用图**。规范: daemon 应该是一个**显式签名的函数** (`def _run(*, assessment_id, db, audit, scope_enforcer, ...)`), 不读 app.state。

### 3.7 Defense in depth

- v3: 状态机严格 (层 1) + commit 显式 (层 2) + BackgroundTasks (层 3)
- v4: busy_timeout 高 (层 1) + retry (层 2) + Outbox 剥离 (层 3) + PG (层 4)

**单层防御永远会被击穿**——v3/v4 都是"单层假设"被打破。

## 4. 代码实践 (具体可落地的)

### 4.1 显式 Unit of Work (治 v3 + v4)

```python
class UnitOfWork:
    """一个事务 = 一个 connection = 一个 commit point。"""
    def __init__(self, db): self._db = db
    def __enter__(self):
        self._session = self._db.open_session()
        return self
    def __exit__(self, *exc):
        if any(exc): self._session.rollback()
        else: self._session.commit()
        self._session.close()
    @property
    def assessments(self): return SqlAlchemyAssessmentRepository(self._session)
    @property
    def audit(self): return AuditChain(self._signer, store=...)
```

**关键**: `AuditChain.store.append` 接受 `session` 参数,与业务写入**同事务**。

### 4.2 Connection lifecycle hygiene (治 v4 的"每事件新连接")

- **Rule**: 每个逻辑操作最多一个 connection
- **Tool**: `contextlib.contextmanager` 包装 session 生命周期
- **Linter**: 自定义规则 grep `with self._db.open_session()` in hot path (每事件 = 热路径)

### 4.3 State machines as data (治 v3 的状态机保证)

- **轻量**: `enum` + `@runtime_checkable Protocol` per state (XState 风格的 typed transitions)
- **重量**: XState / statecharts
- **本项目**: assessment lifecycle 已经在 `domain/assessments/models.py` 用 enum——可以加 `assert_transition(from, to)` 的协议, 把 "raise" 变成"类型拒绝"

### 4.4 显式 background work (治 v3 的 daemon pattern)

- **轻量**: FastAPI `BackgroundTasks` (FastAPI 保证 response flush+commit 后才跑)
- **重量**: 真正的 job queue (`arq`, `rq`, `temporal`)

**本项目短期**: `BackgroundTasks` 即可;长期如果 orchestrator 经常跑 >10 分钟或需要暂停/恢复, 迁到 `arq` (Redis-backed, 纯 Python 异步, 轻量)。

### 4.5 No hidden state / DI 注入 (治 v3 的 shadowing)

- **Rule**: 函数内不 `new` 依赖性对象 (DB、repo、audit、signer)——全部通过参数注入
- **反例**: `execution.py:279` 在函数内 `audit = AuditService(audit_repo)` shadowing 参数 `audit`
- **正例**: 所有依赖通过参数显式传入, 函数体只做编排

### 4.6 "Fails fast, fails loud" (治所有"silent suppression")

v3 的 `service.fail()` raise 被 `contextlib.suppress(Exception)` 吞掉——**导致状态机不一致且无任何信号**。规范:
- `contextlib.suppress` **必须**有注释解释"为什么这里安全吞"
- 任何"应该让错误传播"的地方,**不要** catch
- 测试**专门**断言"这个错误没有被吞"

### 4.7 Idempotency keys (治 daemon 重启 + 重试)

`start_assessment` 第二次调用会 raise "cannot start from queued"——但 daemon 已经因为 race 失败后, 状态是"queued + 写了一个 assessment.failed audit",**没有机制重试**。规范: 每个 long-running operation 有 idempotency key (前端生成 → 路由用 → daemon 校验 → 重复请求安全 no-op)。

### 4.8 Logging as a first-class concern (治"看不见的失败")

v3 触发后, `assessment.failed` audit 写了,但**没有任何日志说"daemon 看到 APPROVED, 可能是 race"**。规范:
- 任何"在 daemon / background worker 里的 catch"必须 log `exc_info=True` + 结构化字段
- 任何"silent fallback"必须有 metric/alert

### 4.9 Test environment == Production environment (治 v3/v4 的测试盲点)

```python
# conftest.py
@pytest.fixture
def engine(tmp_path):
    eng = create_sqlite_engine(tmp_path / "t.db")
    # 强制与 prod 一致: NullPool, WAL, busy_timeout=5000
    return eng

# 测试不再用 sqlite:///:memory: (StaticPool)
# 或者显式: StaticPool 只用于"单连接无状态"测试, 标注清楚
```

具体到本项目: orchestrator 的 E2E 测试应该跑**真实 daemon thread + 真实 file DB + NullPool**, 断言 daemon 看到 committed 状态 + 高频 audit 无 OperationalError。

### 4.10 Property-based testing (治 race + 边界条件)

`hypothesis` 库可以**自动**探索边界:

```python
@given(target=st.text(), start_id=st.uuids())
def test_assessment_start_daemon_sees_queued(target, start_id):
    # hypothesis 自动跑 N 次
    # 任何一次 daemon 看到 APPROVED = v3 race = test fails
```

v3 这种 race 在 1 次手写测试中可能不触发 (依赖时序), hypothesis 跑 1000 次会高概率触发。

## 5. 框架与库 (可以借鉴和复用的)

按"对本项目价值/引入成本"排序:

### 立即引入 (高价值,低成本)

| 框架 | 解决什么 | 引入方式 |
|---|---|---|
| **Transactional Outbox** | v3 + v4 一次解决 | 自实现 (~50 行: outbox 表 + 后台 worker) |
| **FastAPI BackgroundTasks** | v3 的 daemon 模式 | 替换 `threading.Thread` (重构 `start_assessment`) |
| **`hypothesis`** | 边界 + race 自动探索 | 加到 dev deps, 标 `@given` 关键不变量 |
| **`mutmut` / `cosmic-ray`** | 测试质量 (v3/v4 测试通过 = 测试不够强) | CI 跑 |

### 中期引入 (架构级)

| 框架 | 解决什么 |
|---|---|
| **State machines as data** (XState / 自实现 typed states) | v3 类状态机 bug 编译期拒绝 |
| **`arq`** (Redis-backed async job queue) | daemon 模式 (长跑、暂停、重试、分布式) |
| **`pydantic-settings`** | 配置 (12-factor), 替代散落的 `os.environ.get` |
| **`opentelemetry` + structured tracing** | 跨 daemon/request/queue 的 trace (v3 的"看不到"问题) |

### 长期/可选

| 框架 | 何时 |
|---|---|
| **Temporal** | 当 orchestrator 变得复杂 (多个长跑 step、复杂重试、外部交互)—— 太重, 本项目现在不需要 |
| **Event sourcing** (轻量) | 当审计/事件成为核心产品特性时 (v3 已经是事件链, 但没拥抱) |
| **CQRS** | 读多写少且读模型复杂时 (本项目现状不需要) |

### 借鉴的模式 (不是新框架, 是设计模式)

- **Hexagonal / Ports & Adapters** (Alistair Cockburn) —— 本项目已经在用 ports, 继续强化: 每个外部依赖 (DB、文件、HTTP、docker) 都有 port,**业务不知道实现存在**
- **Outbox + Saga** (Vaughn Vernon DDD) —— 大系统的最终一致性
- **The Twelve-Factor App** —— 配置、无状态、并发
- **CAP theorem awareness** —— SQLite = AP-ish (单写者锁 = 牺牲 P), PG = CA-ish。**知道你的数据库的 trade-off**

## 6. 流程 (比代码更能减少 bug)

### 6.1 Deployability-driven development (治"已建未接线")

**Rule**: 每个 PR 必须**回答**: "这个 PR 在真机上跑端到端 assessment 时, 会改变什么?" 如果答案是"不知道"或"组件测试通过"——**PR 不合入**。

**具体**: 维护一个 `docs/architecture/integration-graph.md`, 画清楚 "HTTP request → X → Y → daemon → Z" 的全链路。**每条边必须有端到端测试覆盖**。W2/W3/W4 的"已建未接线"正是因为没有这个图+这些端到端测试。

### 6.2 Production-realism test tier (治 v3/v4 的测试盲点)

建立**第三层**测试 (已有 unit + integration, 加 **production-realism**):
- **Unit** (<1s): 逻辑、纯函数、in-memory DB (快)
- **Integration** (<30s): 组件交互, tmp_path DB (合理)
- **Production-realism** (<5min): **真实 file DB + NullPool + 并发线程 + 长跑**。**每个 release 前必跑**。
  - v3 regression: `start_assessment` × 100 (hypothesis), 断言 daemon 总看到 QUEUED
  - v4 regression: audit storm × 10000, 断言无 OperationalError

### 6.3 "Walking skeleton" before feature

**Rule**: 在写第一个业务功能前, **先跑通最薄的全链路** (一个 endpoint + 一个 daemon + 一个 commit + 一个 audit 持久化)。哪怕只做 1% 的功能, 端到端可工作。然后**所有功能在这个 skeleton 上增量**。

**本项目教训**: v0.1.5 之前没人跑过"完整 assessment 端到端"——直到真机部署才暴露 v2 (0 findings) 和 v3 (race)。**如果开发期就有 production-realism 的端到端测试, v2 + v3 都会在 CI 暴露**。

### 6.4 Pre-commit / pre-merge gates (已部分有, 强化)

```yaml
# pre-commit + CI gates
- format (ruff --fix, black, isort)
- lint (ruff)
- type (mypy strict)
- secret scan (gitleaks)
- test-fast (pytest -x --timeout=30)   # 单元 + 快速集成
- test-realism (pytest -m realism --timeout=300)  # production-realism
- coverage >= 80%
- bandit -ll
- architecture-deps (custom: grep forbidden patterns, e.g. `with self._db.open_session()` in hot path)
```

### 6.5 Postmortem / Blameless (治"重复犯")

v3 + v4 是**同一类问题** (隐式跨边界) 的两个 instance。如果不写 postmortem、归纳"为什么会犯", 下次还会犯——比如 W4-A 的 `DatabaseAuditRecorder` 已经犯同样的错 (每记录 `open_session()`)。

**本项目建议**: 本文档就是 v0.2.0 postmortem;**下一个 release 前**回顾"哪些建议被执行了、哪些没、为什么"。

### 6.6 "The boring technology" + 选择标准

选技术时问 4 个问题:
1. **它是社区主流吗?** (Stack Overflow 答案数、stars、招聘市场)
2. **它解决的是真实问题还是"听起来很酷"?** (Outbox > 区块链, BackgroundTasks > 分布式 saga)
3. **它的失败模式是 well-understood 吗?** (Postgres 的锁 vs SQLite 的锁 vs MongoDB 的锁, 谁的更可预测)
4. **它能被 1 个工程师 1 周内掌握吗?** (如果不能 = 引入成本太高)
